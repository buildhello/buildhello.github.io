Introduction

In the GNU open source software world, ’configure’ is a script created by the ’autoconf’ program, which is part of the GNU autotools suite used to build open source GNU software.

You can read more about the GNU autotools here:

http://freesoftwaremagazine.com/books/autotools_a_guide_to_autoconf_automake_libtool/

Keep in mind that autoconf will compile, link and run source-level feature checks in these languages:

  • C
  • C++
  • Objective C
  • Fortran
  • Fortran 77
  • Erlang

There are many software build tools for other languages, such as Java, Rust, Go, C#, and others, and on native Windows systems it is usually more appropriate to use the excellent free build environments provided there (such as MSVC, MSBuild, and related tools) rather than trying to force GNU autotools into that role.

configure

configure is a shell script — usually auto-generated by autoconf — that prepares your build environment before you run make. Rather than hard-coding assumptions about compilers, libraries, and OS behavior, configure actually tests the system it’s running on and records the results.

In practice, configure:

  • Probes for compilers (cc, gcc, clang, etc.) and their capabilities
  • Checks for required libraries, header files, and functions
  • Detects system features and quirks (e.g., presence of pthread, ncurses, libX11, 64-bit vs 32-bit)
  • Decides where things should be installed (--prefix, --bindir, --libdir, etc.)
  • Optionally enables or disables optional features (--enable-, --with-)
  • Generates project-specific Makefile=s and configuration headers (e.g., =config.h) tailored to your system

Running ./configure with different options directly influences what gets built, what features are compiled in, where files will be installed, and sometimes even which code paths are used to work around platform differences.

An Example of a Configure Command Line Call

./configure \
--with-native-compilation \
--with-pgtk \
--disable-gc-mark-trace \
--with-xft \
--with-zlib \
--with-gnutls \
--with-tree-sitter \
--with-cairo \
--with-modules \
--disable-silent-rules \
--with-mailutils \
--prefix=$HOME/.local/emacs-30.2-wayland \
"CFLAGS=-O3 -march=native -fomit-frame-pointer -fno-math-errno"

With vs Without

In Emacs, if a --with-<feature> configure option exists, a corresponding --without-<feature> option is typically available to disable that feature. This convention is widely followed in the build system, as seen in examples like --with-jpeg and --without-jpeg. However, this is not guaranteed for every option, as some features may be enabled by default and only offer a --without variant, or depend on autoconf logic defined in configure.ac. If you really need exacting customizations, test with both options.

Standard VS Custom configure Options

Although many projects use the GNU Autotools and share a common style of options, each ./configure script is specific to the software it belongs to. Autoconf provides a standard framework and a set of generic options (like --prefix, --help, --host, --build, --disable-dependency-tracking and so on), but the project’s own configure.ac (and related files) define all the project-specific options.

That means:

  • There’s a core set of options that behave similarly across most Autotools projects
  • Every piece of software can (and usually does) add its own custom --enable- and --with- flags that only make sense for that project

Emacs is a good example: it uses the Autotools machinery, so it supports the usual generic options, but it also defines many Emacs‑specific flags to control features like which graphical toolkits are used, whether native compilation is enabled, what kinds of image libraries are linked, etc.

The rest of this page is organized accordingly:

One section explains the standard, project-independent options you’ll see in almost every Autotools-based build system. These include installation prefixes, build/host/target triplets, compiler and flags overrides, and various enable/disable toggles that apply broadly. Understanding these gives you a solid baseline you can reuse for many different packages, not just Emacs.

Another section drills down into Emacs-specific configuration options, which are unique to building Emacs. Here you’ll find flags that control which optional features Emacs is compiled with, which GUI toolkits and libraries are used, and how Emacs interacts with your system’s capabilities.

Together, these two sections show both the general pattern of how Autotools configure scripts work and the concrete details of how Emacs customizes that pattern.

Emacs Specific Configure Options

Graphical backends / window systems (X11, toolkits, Wayland/PGTK)

These options decide whether Emacs is built with a GUI at all, and if so, which window-system “stack” it targets. In 2025 on Linux desktops you typically choose either:

  • PGTK (--with-pgtk) for Wayland-first GTK3 builds (can still run on X via GTK), or
  • X11 (--with-x with a toolkit like gtk) for classic Xorg/Xwayland/SSH-forwarding friendliness.

PGTK and X11-specific knobs generally must not be mixed; when PGTK is enabled, X-specific options are errors.

PGTK [Wayland]

--with-pgtk

Build the “pure GTK” (PGTK) Emacs, which is the Wayland-first GUI port on Linux. Choose this if your desktop is primarily Wayland (GNOME, many modern setups) and you want Emacs to behave like other Wayland-native apps (input methods, HiDPI, compositor integration). When you enable PGTK, you should not also enable X11-specific configure flags, because they target a different window-system stack.

Popular in 2025: common on Wayland desktops.
Dependencies: GTK3 development packages (plus whatever your distro pulls in for GTK).

--with-xwidgets

Enable xwidgets so Emacs can embed WebKit-based views (for example, browsing, HTML-heavy docs, or custom tooling inside buffers). This is only worth enabling if you already know you want web rendering inside Emacs, because it adds a large dependency and can complicate builds and debugging. It’s often paired with GTK builds (including PGTK) when your distro provides compatible WebKitGTK.

Popular in 2025: niche.
Dependencies: WebKitGTK development packages (large), GTK3.

X11

--with-x

Enable the classic X11 GUI build (“Emacs under X”). Pick this if you use Xorg, rely on Xwayland behavior, do remote X11 forwarding (ssh -X/-Y), or run lightweight window managers where X11 is still the main target. This is also the path where the X11-specific include/library path flags and X toolkits apply.

Popular in 2025: still common (especially Xorg/Xwayland and remote use).
Dependencies: X11 development headers/libs (varies by distro; typically libX11 and friends).

--with-x=no

Force a non-X11 build. This is mainly for terminal-only or headless builds (servers, containers, minimal environments), or when you want to avoid pulling in GUI dependencies entirely. If you want a GUI, use X11 (--with-x) or PGTK (--with-pgtk) instead.

Popular in 2025: common for servers/containers; less common on desktops.
Dependencies: none.

--x-includes=DIR[:DIR…]

Manually point configure at non-standard locations for X11 header files. Usually you only need this in cross-compiles, sysroot builds, or when X11 is installed under a custom prefix where Autoconf doesn’t search by default. For normal distro installs, you leave this unset.

Popular in 2025: rare.
Dependencies: none by itself (but only meaningful with X11 enabled).

--x-libraries=DIR[:DIR…]

Manually point configure at non-standard locations for X11 libraries. This matters in the same kinds of “unusual layout” cases as --x-includes (custom prefix, sysroot, cross toolchain), and is often paired with appropriate LDFLAGS. In typical desktop builds, the system linker paths already cover this.

Popular in 2025: rare.
Dependencies: none by itself (but only meaningful with X11 enabled).

--with-x-toolkit=TOOLKIT

Choose which widget toolkit Emacs uses on top of X11 for menus/dialogs. This option only applies to X11 builds and is where you decide between GTK (most common), or lower-dependency/legacy toolkits like Athena or Motif. If you’re aiming for “normal desktop integration” on X11, you typically pick GTK.

Popular in 2025: common to set implicitly/explicitly (non-GTK choices are niche).
Dependencies: depends on selected toolkit + X11.

--with-x-toolkit=gtk

Use GTK on top of X11 (GTK-on-X11, not PGTK). This is a good choice when you want X11’s behavior and compatibility (including remote X forwarding), but also want GTK theming and desktop integration. Many distros historically shipped this as the default GUI Emacs variant.

Popular in 2025: common on Xorg/Xwayland systems.
Dependencies: GTK3 development packages + X11.

--with-x-toolkit=athena

Use the lightweight Athena (Xaw) toolkit. This is primarily for low-dependency systems or minimalist setups where you still want an X11 GUI but don’t want the GTK stack. Expect a more “classic” look and fewer integration perks compared to GTK.

Popular in 2025: niche.
Dependencies: Xaw development libraries + X11.

--with-x-toolkit=motif

Use Motif widgets on X11. This is mostly a legacy/compatibility choice and may be relevant only in specialized environments that still standardize on Motif. For most students building Emacs today, GTK is the practical option unless you have a specific reason to match Motif-based desktops.

Popular in 2025: uncommon.
Dependencies: Motif development libraries (may be non-default) + X11.

--with-xwidgets

Enable xwidgets so Emacs can embed WebKit-based views under an X11 GUI build. This is useful for specialized workflows, but it increases build time, binary size, and dependency surface area, so it’s best treated as an opt-in feature rather than a default.

Popular in 2025: niche.
Dependencies: WebKitGTK development packages (large), GTK3 (commonly), X11.

Native compilation (Elisp → native code via libgccjit)

These options control whether Emacs produces .eln native-compiled Elisp. They interact with your toolchain and packaging choices.

--with-native-compilation

Native compilation lets Emacs turn some Elisp into native .eln code using libgccjit, which can noticeably speed up startup, package loading, and heavy interactive workloads once your configuration grows. This is mainly about matching what modern distros ship and avoiding surprises later: if your system packages expect native compilation (or you install lots of Elisp), having it enabled gives you the “normal 2025” Emacs experience and fewer performance bottlenecks to chase.

Popular in 2025: yes (where libgccjit is packaged).
Dependencies: libgccjit (development package) and a GCC toolchain compatible with that libgccjit build.

--with-native-compilation=aot

AOT native compilation builds (almost) all bundled Elisp into .eln files during build/install instead of deferring compilation to first run via JIT. This is useful when you want a predictable, reproducible build artifact (helpful for packaging, lab machines, or shared environments) and you’d rather “pay” the compile cost once during build time than have Emacs compile things on demand after you install it. AOT is also a good way to verify your compiler/libgccjit setup is solid because failures show up during the build.

Popular in 2025: moderately (packagers/power users).
Dependencies: same as native compilation; expect longer build/install time and more disk usage for .eln outputs.

--with-native-compilation=no

Disabling native compilation forces Emacs to run purely on byte-compiled .elc (or interpreted) Elisp, which can simplify builds on minimal systems and avoids dealing with libgccjit compatibility issues. If you’re building from source on unusual hardware, inside constrained containers, or you’re debugging regressions that appear only with .eln output, this option helps you produce a “baseline” Emacs that is easier to reproduce across machines. It’s also relevant if you need a policy of “no generated native artifacts” in your install tree.

Popular in 2025: still used in minimal/compat builds.
Dependencies: none.

TLS / cryptography (network security)

These options control whether Emacs can do HTTPS/TLS for packages, URL libraries, and many integrations.

--with-gnutls

Build Emacs with GnuTLS support when it’s detected, but don’t fail the build if it isn’t. This is mainly useful when you’re compiling from source in “unknown” environments (minimal containers, odd CI runners, experimental ports) where TLS libraries may or may not be installed, and you still want some Emacs binary out the other end. The key takeaway is what you’re trading off: if GnuTLS isn’t found, you’ll get an Emacs that can’t do HTTPS properly – meaning package archives (GNU ELPA/MELPA), many URL-based libraries, and a lot of integrations will be broken or severely limited, which can make the build feel “mysteriously unusable” even though compilation succeeded.

Popular in 2025: mostly niche/packaging CI, enabled by default if dependencies are present
Dependencies: optional; when present needs the GnuTLS development package (often libgnutls-dev).

JSON parsing

These options decide whether Emacs uses a C JSON library (fast) vs pure Elisp (slow). This matters a lot for LSP and JSON-heavy tooling.

--with-json

This enables Emacs to use an external C JSON library (most commonly Jansson) instead of the built-in pure-Emacs-Lisp JSON routines. If you plan to build Emacs from source and then use modern developer workflows—LSP clients, language servers that speak JSON-RPC, package tooling that exchanges lots of JSON—this option is a practical performance win: parsing is faster, GC pressure is lower, and UI hiccups during heavy JSON traffic are reduced. However, on a typical 2025 Linux build, there is a new native JSON parser that does not rely on Jansson (introduced in Emacs 30.1+). It’s built in and up to 8x faster, rendering the jansson library obsolete.

Popular in 2025: enabled by default in Emacs 30.2 if the jansson library is present
Dependencies: Jansson development package (e.g., libjansson-dev).

--without-json

This forces Emacs to avoid any external JSON library and fall back to the pure-Elisp implementation. It can be useful when you’re doing a “smallest possible” build, validating that your build works without optional libraries, or when you’re in a constrained environment where adding system dependencies is undesirable. The tradeoff is that JSON-heavy features (notably LSP/JSON-RPC traffic) can feel noticeably slower, which is exactly the kind of friction you’ll notice after compiling Emacs and setting it up for programming.

Popular in 2025: niche.
Dependencies: none.

--with-jansson

This explicitly selects Jansson as the JSON backend, which is mainly relevant when you want to be unambiguous about which library your from-source build will link against (for example, in packaging, reproducible builds, or when multiple JSON options exist on a platform). In many setups it ends up being functionally similar to --with-json because Jansson is the expected provider, but this flag can help when you’re troubleshooting configure results or ensuring the build uses the fast C path you intended.

Popular in 2025: niche/packaging [obsolete]
Dependencies: Jansson development package.

--without-jansson

This tells configure not to use Jansson even if it’s installed. It’s mostly useful for testing (e.g., confirming Emacs still builds and runs without that optional dependency), or for environments with policy reasons to avoid linking against it. It’s usually counterproductive because it pushes you back toward slower JSON handling and can make JSON-RPC/LSP workloads less pleasant.

Popular in 2025: rare.
Dependencies: none.

Tree-sitter parsing

Tree-sitter provides fast incremental parsing used by modern major modes for better font-lock and structural editing.

--with-tree-sitter

Tree-sitter enables Emacs to use fast, incremental syntax parsing, which many newer major modes rely on for more accurate highlighting, indentation, navigation, and “structural” editing features. If you’re building Emacs from source in 2025 and plan to work on code (or evaluate modern mode behavior), enabling this makes your build closer to what most developers expect; you’ll still install individual language grammars separately, usually via packages.

Popular in 2025: Common for developer builds (enabled by default if the treesitter dependencies are available on the system)
Dependencies: The tree-sitter development library (e.g., libtree-sitter-dev, plus headers).

--without-tree-sitter

Disabling tree-sitter produces a smaller, simpler Emacs that sticks to the classic regex-based font-lock and mode logic. This can be useful if you’re targeting a minimal system, building for a platform where the library isn’t readily available, or you want to reduce moving parts while learning the core build process; some modern language modes may provide fewer features or fall back to older behavior.

Popular in 2025: Less common; mainly minimal or constrained builds.
Dependencies: None.

Image and graphics formats

These control which image formats Emacs can display. They interact strongly with GUI builds: when X11 support is enabled, several image libs are “strongly recommended” and configure may error if missing unless you explicitly disable them with --without-.

--with-xpm / --without-xpm

XPM is an older X11 icon/pixmap format that Emacs can use for toolbar icons, some theme assets, and X resources in GUI builds. When you build Emacs from source on Linux/X11, keeping XPM support tends to reduce surprises (missing icons or fallback graphics), but it does add the legacy libXpm dependency that some minimal or hardened systems prefer to avoid. If you are aiming for a small, dependency-light build (or you are not using X11), disabling it is a reasonable choice.

Popular in 2025: Enabled by default if the Xpm development libraries are present.
Dependencies: libXpm.

--with-jpeg / --without-jpeg

JPEG support matters mainly for viewing images inside Emacs (for example, documentation, emails, or web content displayed in buffers) and for packages that preview media. Disabling JPEG is usually self-inflicted pain: you lose a common format and may run into “cannot display image” issues in workflows you didn’t anticipate. It only makes sense for strict server/TTY builds, or when you are deliberately minimizing optional libraries to simplify your toolchain.

Popular in 2025: Enabled by default if libjpeg (and headers) are present.
Dependencies: libjpeg.

--with-tiff / --without-tiff

TIFF is less common day-to-day, but it shows up in scanned documents, academic material, and some publishing workflows. From a “build Emacs from source” perspective, the main question is whether you want a broadly capable GUI editor or a minimal binary with fewer external libraries to manage. Disabling TIFF is low-impact, but if you later work with PDFs/images converted to TIFF (or use packages that expect it), you’ll need to rebuild with libtiff enabled.

Popular in 2025: Enabled by default if libtiff (and headers) are present.
Dependencies: libtiff

--with-gif / --without-gif

GIF support enables display of GIF images, including simple animations, inside Emacs buffers. While GIF is not a “core editor” requirement, it still appears in READMEs, issue trackers, and web-derived content that you might read from within Emacs. Keeping GIF avoids small annoyances; disabling it is mostly about trimming one more optional dependency in minimal builds or controlled environments.

Popular in 2025: Enabled by default if giflib (and headers) are present.
Dependencies: giflib

--with-png / --without-png

PNG is one of the most common formats for UI assets (icons, screenshots, images in docs), and many Emacs packages assume PNG rendering works. If you’re compiling Emacs from source for a desktop setup, disabling PNG often leads to a degraded experience: missing toolbar icons, broken image previews, and confusing “image type not supported” messages. It’s mainly used for extreme minimization or unusual environments where you want to avoid carrying libpng (and its transitive requirements) in your build inputs.

Popular in 2025: Enabled by default if libpng (and headers) are present.
Dependencies: libpng + zlib.

--with-rsvg / --without-rsvg

This disables SVG rendering via librsvg, which is increasingly relevant because SVG is common in modern icon sets, documentation, and Org/HTML export pipelines. You might disable it if you want fewer GNOME/GLib-related dependencies, or if you are aiming for a minimal Emacs that avoids larger library stacks.

Popular in 2025: Enabled by default if librsvg (and headers) are present.
Dependencies: librsvg2

--with-webp / --without-webp

WebP is widely used on the web, so it can matter if you read web-derived content in Emacs (RSS, emails, eww, or packages that fetch images). It’s not essential for Emacs itself, but having it can reduce friction when viewing modern image assets without external conversion. When building from source, disabling WebP is mainly a dependency-trimming move: you accept that some images won’t render and you keep your build inputs simpler.

Popular in 2025: Enabled by default if libwebp (and headers) are present.
Dependencies: libwebp.

--with-imagemagick

This enables ImageMagick integration, giving Emacs access to a huge range of image formats and some image processing features. When building from source, it’s tempting as a “support everything” switch, but it comes with real tradeoffs: a larger dependency chain, more moving parts during compilation, and historically higher security/policy sensitivity (many distros lock it down). Use it when you specifically need uncommon formats or transformations inside Emacs and you’re comfortable maintaining ImageMagick safely on your system.

Popular in 2025: niche (policy-sensitive).
Dependencies: ImageMagick development packages (and their dependency chain).

--with-cairo

Cairo is a modern 2D drawing library that Emacs can use for GUI rendering, typically improving text and shape rendering quality and aligning better with contemporary Linux graphics stacks. Cairo is often a “make it feel modern” option, especially alongside current font libraries (FreeType/Fontconfig/HarfBuzz). If you’re doing a terminal-only build it doesn’t matter, but for X11/Wayland GUI builds it’s a common, practical choice.

Popular in 2025: yes.
Dependencies: Cairo development libraries.

--with-cairo-xcb

This selects Cairo’s XCB backend (relevant only to X11 builds) and can matter for advanced setups where you care about how Emacs talks to the X server (performance characteristics, latency behavior, and integration details). For most people building Emacs from source, it’s not worth enabling unless you know you want XCB specifically, because it increases the surface area for display-related issues and is sometimes avoided due to reports of instability in certain lifecycle paths. Treat it as a specialist option for X11 tuning.

Popular in 2025: rare.
Dependencies: Cairo with XCB support + XCB libraries.

Text shaping / fonts (HarfBuzz, FreeType, Fontconfig, Xft)

These control font discovery and shaping quality. In 2025, for GUI builds, a typical “good typography” stack is: --with-harfbuzz + --with-freetype + --with-fontconfig (and on X11 often --with-xft).

Disabling them is mainly for minimalism or troubleshooting.

--with-harfbuzz

HarfBuzz is what makes Emacs render modern text correctly: ligatures, combining marks, and shaping for complex scripts (Arabic, Indic, etc.). If you’re building a GUI Emacs from source on Linux in 2025, enabling it is the “default good” choice because it avoids subtle rendering bugs and makes font behavior match what other modern apps do.

Popular in 2025: Yes, enabled by default if HarfBuzz libraries are present.
Dependencies: HarfBuzz development package.

--without-harfbuzz

This forces Emacs to build without HarfBuzz even if it’s installed. It’s mainly useful when you’re debugging font/shaping issues, trying to reduce dependencies for a minimal build, or targeting an environment where HarfBuzz isn’t available; the tradeoff is that some scripts and typographic features will render incorrectly or inconsistently.

Popular in 2025: niche.
Dependencies: none.

--with-freetype=

FreeType provides the font rasterizer that turns font outlines into pixels, and it’s a core part of “nice-looking” GUI text on Linux. Enabling it is important because most distro GUI stacks assume FreeType, and disabling it often leads to worse rendering or fewer usable font paths.

Popular in 2025: Enabled by default if freetype2 (and headers) are present and you are building a GUI Emacs that uses font backend features.
Dependencies: FreeType development package.

--without-freetype

Disabling FreeType is mostly for unusual platforms, constrained builds, or isolating rendering problems. In a typical 2025 Linux GUI setup, it’s rarely what you want because it removes the standard rasterization path and can make fonts look worse or limit which fonts Emacs can practically use.

Popular in 2025: rare.
Dependencies: none.

--with-fontconfig

Fontconfig is the “font discovery and fallback” system on most Linux desktops: it finds installed fonts, selects substitutes, and handles sane defaults. When you build Emacs from source, enabling it saves you from manual font headaches and makes Emacs follow the same font configuration as the rest of your system.

Popular in 2025: enabled by default when the dependencies are found.
Dependencies: Fontconfig development package.

--without-fontconfig

This turns off Fontconfig integration, which is mainly attractive for minimalism, controlled environments, or debugging font selection. The downside is that Emacs may have a much harder time finding fonts and doing fallback correctly, so you can end up chasing missing glyphs or strange default choices.

Popular in 2025: rare.
Dependencies: none.

--with-xft

Xft is the X11-era font rendering interface that typically sits on top of FreeType + Fontconfig for X builds. If you’re compiling an X11 GUI Emacs from source (not pure GTK/Wayland-only setups), this is commonly enabled because it gives you the expected anti-aliased font rendering and integrates well with the rest of the X stack.

Popular in 2025: Enabled by default when dependencies are found.
Dependencies: Xft development package (usually plus FreeType and Fontconfig).

--without-xft

This disables Xft for X11 builds, which is mostly useful for simplifying the dependency graph or narrowing down rendering issues. For everyday X11 GUI use, it can reduce text quality or make font behavior less consistent with typical Linux desktop rendering.

Popular in 2025: rare.
Dependencies: none.

--with-libotf

libotf is an older OpenType support path that historically mattered for complex text handling. In a modern 2025 build, HarfBuzz is generally the relevant shaping engine, so libotf is mostly about compatibility with older configurations or niche platforms where it’s still used as part of a legacy text stack.

Popular in 2025: low (legacy/compat).
Dependencies: libotf development package.

--without-libotf

This excludes libotf, which is common if you’re aiming for a cleaner, modern dependency set and you already rely on HarfBuzz for shaping. It’s a reasonable choice for most builds on contemporary Linux, unless you specifically need legacy text-stack compatibility.

Popular in 2025: moderate (minimal/modern builds).
Dependencies: none.

--with-m17n-flt

m17n-flt is another historical complex-script shaping path used in some setups. In practice, if you enable HarfBuzz you usually don’t need this, but it can still matter on certain systems or when you’re reproducing older build environments for research, packaging, or compatibility testing.

Popular in 2025: low (legacy/compat).
Dependencies: libm17n-flt (and related m17n components) development packages.

--without-m17n-flt

This disables m17n-flt support, which is a common way to trim legacy shaping dependencies when HarfBuzz is present. For a typical 2025 source build focused on mainstream Linux desktop behavior, leaving it off keeps the build simpler.

Popular in 2025: moderate.
Dependencies: none.

--with-lcms2

LCMS2 adds color management support, which can matter if you care about accurate color profiles (e.g., image work or color-critical displays). For most Emacs users it won’t be noticeable, but when building from source it’s a sensible optional feature if your system already uses color management and you want Emacs to participate cleanly.

Popular in 2025: Enabled by default if the dependencies are present.
Dependencies: lcms2 development package.

--without-lcms2

This omits LCMS2, which is a typical choice when you’re minimizing optional libraries or building in a constrained environment. Unless you specifically rely on color-managed workflows, most users won’t miss it, so it’s an easy dependency to drop.

Popular in 2025: moderate (minimal builds).
Dependencies: none.

System integration (D-Bus, systemd, file notifications)

These affect how Emacs integrates with a modern Linux desktop/session and how it detects file changes.

--with-dbus / --without-dbus

Disable building Emacs with D-Bus support, meaning Emacs won’t talk to the desktop “message bus” that many Linux components use for session services. This mainly matters because D-Bus is how Emacs can integrate with things like desktop portals, some settings backends, and certain GUI session behaviors; in headless or SSH daemon setups you may prefer to avoid Emacs trying to connect to (or auto-start) a session bus. It’s also a straightforward way to ensure your build never depends on D-Bus-related libraries.

Popular in 2025: common for servers/daemons; uncommon for desktop builds. Enabled by default if dbus and its development headers are present.
Dependencies: none (it avoids needing D-Bus development libraries).

--with-libsystemd

Build Emacs with optional systemd integration, which is primarily relevant when Emacs is run as a service (or is tightly integrated into a distro’s service/session management). If you’re building Emacs from source for personal use, you won’t notice this feature day-to-day; it tends to matter more for packaging, for daemon service-style deployments, and for environments where you want Emacs to participate cleanly in systemd managed life-cycles. It’s worth considering if you intend to run emacs as a long-lived daemon under systemd user services.

Popular in 2025: Enabled by default if libsystemd (and headers) are present.
Dependencies: libsystemd development package.

--without-libsystemd

Force Emacs to build without systemd support, keeping the resulting binary more portable across non-systemd systems and avoiding one more optional integration layer. This is a common choice when you want a “plain Emacs” that behaves the same across machines (including containers, minimal installs, or non-systemd distros), and when you don’t plan to manage Emacs via systemd services. It can also simplify troubleshooting by removing service-manager-specific behavior from the equation.

Popular in 2025: Popular in 2025: common in custom/minimal builds.
Dependencies: none.

--with-file-notification

Enable Emacs’s file notification backend (on Linux typically inotify), which lets Emacs learn about file changes without polling. For a source build, this is one of the most practically useful integrations: it improves features like Auto Revert mode, helps file/tree UIs stay in sync, and makes modern workflows (LSP servers, project tools, build outputs) feel responsive because Emacs can react quickly when files change on disk. On a normal Linux desktop, you almost always want this enabled unless you have a very constrained environment.

Popular in 2025: Popular in 2025: standard/desirable for most desktop builds.

Toolchain and dependency discovery overrides (environment variables)

These variables are the primary knobs for telling ./configure which compilers, flags, directories, and link options to use. They are honored by most Autoconf/Automake–based projects, not just Emacs, and they combine with feature flags like --with-json, --with-pgtk, --with-modules, etc.
They are especially important when: installing into non‑standard prefixes (e.g. /opt, $HOME/opt); using Nix/Guix or other “pure” environments; mixing /usr, /usr/local, and, custom prefixes; cross‑compiling; and using non‑default toolchains (e.g. Clang instead of GCC, LLD instead of BFD, musl instead of glibc).

CC

CC selects the C compiler used for all configure tests and for building Emacs itself (gcc, clang). It matters most when you are cross‑compiling (the compiler must match the target), or when you intentionally want a non-default toolchain such as Clang instead of GCC. For normal native builds on mainstream distros, leaving CC unset (letting configure pick cc) is usually fine.

Popular in 2025: common.
Dependencies: chosen compiler.

CFLAGS

CFLAGS controls the C compiler flags used for both the configure checks and the final Emacs build (optimization, debug info, hardening, CPU tuning). It matters most when you are chasing performance, building debug/test binaries, or producing portable binaries for redistribution. For normal native builds, sticking to conservative, widely-tested flags (typically -O2) is usually best; aggressive tuning can make builds less stable or less portable.

Popular in 2025: common (packaging/custom builds).
Dependencies: chosen compiler (flags must be supported by it).

CFLAGS Examples:

“-0s, -02, -03, -march=native, -mtune=native, -fno-math-errno, -fsanitize=undefined, and -g” are typical emacs CFLAGS.

-Os

-Os (optimize for size) disables some important optimizations and can hurt performance.

-02

-O2 is considered safe and well-tested; -O3 adds marginal speed at potential stability cost.

-03

Aggressive optimizations, like -03 can trigger compiler bugs or cause undefined behavior in complex C code like Emacs.
Some optimizations may break assumptions in the code (e.g., aliasing, strict overflow).

-march=native

-march=native tells GCC to generate code specifically for the CPU that is compiling Emacs. It enables all instruction sets and features that this CPU supports (for example SSE4.2, AVX, AVX2, etc.). The resulting binary may be faster on this machine, but it will likely not run on older or different CPUs that lack those instructions. When you use `-march=native`, GCC automatically implies `-mtune=native` as well, so you do not need to specify both.

-mtune=native

-mtune=native asks GCC to optimize instruction scheduling and other CPU-specific heuristics for the local machine, while still generating code that remains compatible with the baseline architecture (typically generic x86-64). Unlike -march=native, it does not enable new instruction sets, so the resulting binary is more portable but usually gains a smaller performance improvement. If you want a build that runs on many different machines, -mtune=native is generally safer than -march=native.

-fno-math-errno

By default, GCC assumes math functions (like sqrt, log) may set errno on error, which limits some optimizations. -fno-math-errno tells GCC not to preserve errno for these functions, enabling faster and more aggressive inlining and vectorization. This is safe if your code does not rely on checking errno after math calls (which most C programs, including Emacs, normally do not).

Recommended for performance: it is reasonable to include -fno-math-errno in CFLAGS.

-fsanitize=undefined

-fsanitize=undefined enables the Undefined Behavior Sanitizer (UBSan). It inserts runtime checks for many forms of undefined behavior (out-of-range shifts, invalid casts, signed integer overflows in some contexts, and more). This is extremely useful for debugging and finding subtle bugs, but it adds noticeable runtime overhead and it can cause Emacs to abort when undefined behavior is detected (including in system libraries). Use -fsanitize=undefined for debugging or test builds, not for production or for binaries you distribute to others.

-g

`-g` tells GCC to include debug information in the compiled binaries. This does not normally change how Emacs runs, but it makes backtraces, core dumps, and interactive debugging (with tools like gdb or lldb) much more informative. The file size grows somewhat, and builds can be slightly slower, but the runtime performance impact is usually negligible. Including -g in 2025 remains very common and is widely recommended, especially for development builds or when you might want to report bugs with useful backtraces.

CPP

CPP selects the C preprocessor command (often cpp or CC -E) that Autoconf uses for header/feature checks. It rarely needs manual setting, but can matter in cross builds, sysroot setups, or unusual toolchains where configure guesses the wrong preprocessor.

Popular in 2025: rare.
Dependencies: toolchain.

CPPFLAGS

CPPFLAGS are extra preprocessor flags, most often -I include paths or -D macro defines, used during configure tests and compilation. It matters when dependencies are installed in nonstandard prefixes (e.g. $HOME/opt, /opt/local) and you need Emacs to find headers like libxml2, imagemagick, or tree-sitter.

Popular in 2025: common in custom prefix builds.
Dependencies: none.

LDFLAGS

LDFLAGS are extra link flags, typically -L library search paths and linker options (including rpath). It matters when libraries live outside the default linker search path, or when you need specific linker behavior (hardening flags, alternate linkers, custom rpaths). For distro builds, these are often injected by the packaging system.

Popular in 2025: common in packaging/custom deps.
Dependencies: none.

LIBS

LIBS appends extra -l libraries to the final link commands. It is mostly a workaround when configure’s library detection does not add a needed library automatically, or when doing unusual static or cross linking. For typical builds, you should prefer fixing pkg-config, CPPFLAGS, and LDFLAGS rather than forcing LIBS.

Popular in 2025: occasional.
Dependencies: external libraries; link order..

PKG_CONFIG

PKG_CONFIG selects which pkg-config executable configure should use to discover compiler and linker flags for dependencies. It matters when you have multiple environments (Nix/Guix, custom prefixes), or in cross-compilation where you need a target-aware wrapper so you don’t accidentally pick up host libraries.

Popular in 2025: common in non-default environments.
Dependencies: pkg-config; dependency .pc files.

PKG_CONFIG_PATH

PKG_CONFIG_PATH adds directories to the search path for pkg-config can find .pc files. It matters when you install dependencies into a nonstandard prefix and need configure to find the right .pc metadata without overriding the system defaults.

Popular in 2025: common in custom-prefix builds.
Dependencies: pkg-config; .pc files in custom prefixes.

PKG_CONFIG_LIBDIR

PKGCONFIGLIBDIR replaces pkg-config=’s default =.pc search path entirely. It matters mostly for cross builds and sysroots, where you want to isolate dependency discovery to the target libraries and avoid accidentally linking against host libraries. For ordinary “add one more prefix” use, PKG_CONFIG_PATH is safer.

Popular in 2025: cross-compiling.
Dependencies: pkg-config; sysroot/target .pc files.

CXX

CXX selects the C++ compiler. Emacs is primarily C, so this usually only matters if optional components or configure checks pull in C++ linking, or if you build modules that use C++. In most native builds it can be left to Autoconf defaults.

Popular in 2025: niche.
Dependencies: chosen compiler.

CXXFLAGS

CXXFLAGS are extra C++ compiler flags, analogous to CFLAGS. They matter only when C++ code is actually compiled or linked as part of your build environment (uncommon for stock Emacs). Most users can ignore it.

Popular in 2025: rare.
Dependencies: none.

LD

LD overrides the linker executable. It can matter in specialized toolchains or cross environments, or when you want a specific linker implementation (bfd, gold, lld). For most builds, using CC plus LDFLAGS (e.g. -fuse-ld=lld) is more common than setting LD directly.

Popular in 2025: rare/specialized.
Dependencies: linker.

AR

AR is a static library archiver used to create static libraries (.a files), that are usually part of binutils or LLVM. It matters when cross‑compiling, where the host archiver must match the target,and in unusual toolchains or lto setups where you want llvm-ar instead of GNU ar. For native builds on common distros, you can usually ignore AR.

Popular in 2025: rare.
Dependencies: toolchain.

RANLIB

RANLIB is an indexer for static libraries used mostly for cross builds to generate or update the symbol index in static libraries created by AR. It matters where RANLIB must match the target toolchains where ar and ranlib are split but must be used in tandem. On modern systems, ar may perform indexing automatically and ranlib can be a thin wrapper, but configure still expects it.

Popular in 2025: rare.
Dependencies: toolchain.

STRIP

STRIP is a symbol stripping tool used to remove debug symbols from binaries and libraries before installation (often via make install-strip). For development builds, you often don’t want stripping (to keep debug info). For packaged/production builds, stripping is common to reduce size, and distro packaging systems often manage this automatically.

Popular in 2025: packaging.
Dependencies:binutils strip (or equivalent).
