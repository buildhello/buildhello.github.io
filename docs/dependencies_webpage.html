Build Dependencies | Emacs 30.2 | Ubuntu 25.04 | 2025

Introduction

In this lesson, you’ll learn about the dependencies used to build Emacs—especially the ones that the build systems – like Autoconf, and the configure script it generates, – look for when you compile Emacs yourself.

Think of building Emacs like building a car on a manufacturing floor. The Emacs source code is the main frame, but many features depend on having the right parts available. Your compiler toolchain, for example (GCC on Linux), is like the core machinery needed to assemble the car. Then there are optional parts you can add if they’re available – like libxml2, an XML parsing library used in Emacs by built-in features and packages. During the build, Autoconf and configure “walk the floor,” checking which parts are installed, deciding what can be included, and adapting the build if some parts are missing.

By the end of the lesson, you’ll know which dependencies you need (required parts) and which ones you might want to install on Ubuntu 25.04 before building Emacs (optional parts). You will also know why those choices affect the features you end up with.

Terminology You Need to Know for This Lesson

  • clone (a Git repository): make a local copy of a project’s source code using Git so you can build it yourself.
  • Git checkout: a copy of the source taken directly from Git (often newer/“in progress”), as opposed to a packaged release download.
  • release tarball: a published “snapshot” of the source code for a specific version, bundled as a .tar.* archive, usually already containing generated build scripts.
  • build from source: compile a program yourself from its source code instead of installing a prebuilt binary package.
  • bootstrapping pipeline: the “setup phase” that generates build files (like configure and Makefile templates) before the actual compilation happens.
  • GNU Autotools / autotools suite: the family of tools (autoconf/automake/libtool, etc.) that generates portable configure scripts and Makefiles.
  • ./autogen.sh: a helper script commonly used in Git checkouts to run the bootstrapping tools and generate configure and related files.
  • configure script (./configure): a script that checks what your system has installed and decides which features can be built, producing Makefiles tailored to your machine.
  • probe / detect (libraries/features): the process where configure checks for headers and libraries to decide whether to enable a feature.
  • modular (software): built so optional features are included only if the needed libraries are present; the “core” can build without everything.
  • toolchain: the basic set of build tools needed to compile programs (compiler, assembler, linker, make, etc.).
  • compiler: the program that turns source code (like C) into machine code.
  • Makefile / make: instructions and a tool that drives the build—what to compile, in what order, and with which flags.
  • template Makefile (Makefile.in): an “input” Makefile that configure fills in to produce the final Makefile.
  • header files / headers: development files (usually .h) that declare library functions and types; needed when compiling code that uses a library.
  • development files / “-dev” packages: packages that contain headers and other build-time files; different from runtime-only libraries.
  • include paths: directories the compiler searches to find header files.
  • linker: the tool that combines compiled code with libraries to produce the final executable.
  • linker flags: options passed to the linker to say which libraries to use and where to find them.
  • shared libraries: libraries that are linked at runtime (the executable depends on them being present on the system).
  • macros (in build systems): reusable snippets/definitions used by the build tools (often autoconf/libtool) to generate configuration logic.
  • cross-distro differences: the fact that different Linux distros package and name build dependencies differently even when they provide the same capability.
  • runtime: what must be available when you run Emacs (as opposed to what’s only needed while building it).
  • terminal / TTY mode (-nw): running Emacs inside a text terminal instead of a GUI window.
  • GUI toolkit: a library framework (like GTK) that provides windows, menus, input handling, etc. for graphical apps.
  • rendering stack: the set of libraries responsible for drawing text and graphics (fonts, shaping, 2D drawing).
  • text shaping: handling complex scripts, ligatures, and correct positioning of characters (important for “modern typography”).
  • Wayland vs X11: two different Linux display systems; which one you build for affects which GUI-related pieces are needed.
  • TLS / HTTPS support: encryption used for secure network connections (important for secure package downloads and web connections).
  • compression: storing/transporting data in a smaller form (often used in archives and some network/file contexts).
  • XML / JSON parsing libraries: system libraries that let software read structured data formats used by configs, metadata, and web-related tooling.
  • SQLite (embedded database): a lightweight local database engine used by some Emacs features/packages for structured storage.
  • ACL (Access Control Lists): an extended permissions system for files beyond basic owner/group/other permissions.
  • bignum / big-integer math: support for very large integers beyond normal machine-sized integer limits (sometimes accelerated by external libraries).
  • image format support: ability to display certain image types (PNG/JPEG/SVG/etc.) when the corresponding libraries are present at build time.
  • attack surface: how much code (especially complex parsers) you’re pulling in that could potentially contain security vulnerabilities.
  • native compilation / “native-comp”: compiling Emacs Lisp into native machine code to improve performance.
  • JIT (just-in-time compilation): compiling code at runtime rather than ahead of time; native-comp relies on JIT infrastructure.
  • version matching (toolchain/library): the idea that some build features work best (or only) when library versions line up with the compiler version.
  • tree-sitter: an incremental parsing system used for better syntax highlighting and structural code understanding.
  • incremental parsing: updating a parse tree efficiently as you edit, instead of re-parsing the whole file each time.
  • xwidgets: embedding external GUI widgets (like a web view) inside Emacs buffers.
  • WebKit-based web rendering widget: the heavy browser-engine component used when embedding web content.
  • integration with external tools: configuring Emacs to use system utilities (for example, certain mail-moving workflows).
  • obsolete / no longer typically needed: dependencies that older guides mention but which modern versions usually don’t require anymore.

Dependencies (Ubuntu 25.04) — build Emacs 30.2 from source

This section explains what each dependency does in an Emacs build, and whether you still need it for a Linux build in 2025. The key idea is that Emacs is modular: the core editor will build with just a compiler toolchain, but many “modern Emacs” features (TLS, images, SQLite, tree-sitter, native-comp) only appear if the right libraries are present when you run ./configure. The following section lists those libraries and explains their function.

Autotools - If building from a Git checkout (required for ./autogen.sh)

When you clone Emacs from Git, the build system isn’t fully generated yet. Running ./autogen.sh prepares the configure script and other build files, and that preparation step relies on the GNU Autotools suite.

autoconf

Autoconf generates the configure script. That script is the part that probes your system (“Do you have GnuTLS? Where is libxml2?”) and then decides which Emacs features can be built. In 2025, you generally only need autoconf if you build from Git. Release tarballs usually already ship a pre-generated configure.

automake

Automake helps generate the Makefile in templates that configure later turns into real Makefiles. It’s part of the same bootstrapping pipeline as autoconf. Like autoconf, it’s typically only required for Git builds, not for release tarballs.

autopoint

Autopoint is part of the gettext/internationalization tooling. It sets up the translation infrastructure so Emacs can build with localized messages and catalogs. If you run ./autogen.sh from a Git checkout, you normally want this installed.

libtool

Libtool provides macros and helper scripts that smooth over differences in how shared libraries are built on different systems. Emacs does not always strictly require it in every configuration, but it often shows up during bootstrapping on some distros and setups. For a Git build in 2025, it’s best treated as “strongly recommended”: if autogen.sh complains, installing libtool is usually the fix.

Build tools (required)

You can’t compile anything without these pieces.

build-essential

On Debian/Ubuntu-family systems, build-essential is the standard meta-package that pulls in GCC, make, and the basic C/C++ development environment. Yes, you still need an equivalent toolchain in 2025. On other distros the package names differ, but the concept is the same.

pkg-config

Emacs’ configure script needs to find lots of optional libraries. pkg-config is the tool that tells configure the correct include paths and linker flags – for example, where GTK or GnuTLS headers live. In practice, a 2025 “full-featured” build is much smoother with pkg-config, and many features may fail to auto-detect cleanly without it.

libncurses-dev

Even if you primarily use a GUI Emacs, you usually still want solid terminal support for emacs -nw, remote sessions, and TTY behavior. libncurses-dev provides the terminfo/terminal capability interfaces Emacs uses for that. In 2025 it’s still recommended, and it’s effectively required if you care about terminal Emacs working well.

texinfo

Emacs manuals are written in Texinfo (.texi) and are compiled into Info documents during the build. If you want C-h i to include freshly-built manuals from your source tree, you need texinfo. This is optional in 2025: many people skip it and rely on prebuilt docs from distro packages or online documentation.

Core runtime/security features

These libraries are not “required” to compile the binary in the strictest sense, but they are what make an Emacs build feel modern and usable in today’s modern workflow environments.

libgnutls-dev

GnuTLS gives Emacs TLS support, which is what you need for HTTPS package archives (ELPA/MELPA), secure connections, and signature checks. Without it, you can end up with a broken network experience. For a 2025 Linux build, you basically want this, unless you have a specialized offline setup.

zlib1g-dev

Zlib adds compression support. Emacs uses it for working with compressed data in various contexts, and it is also used by other libraries Emacs may link against. It’s still a good default to include in 2025. Typically, if configure sees it, you want Emacs built with it.

libxml2-dev

Libxml2 is the XML parsing library Emacs uses for several built-in features and for packages that read XML-based formats. It’s a “quietly important” dependency that helps many things work without you having to think about them. It’s still recommended for any general-purpose build.

libsqlite3-dev

SQLite support has become increasingly relevant since Emacs 29, and continues into Emacs 30-era workflows. If you want Emacs features and packages that store/query structured data efficiently, having SQLite available at build time is a big plus. It’s strongly recommended for a “modern” Emacs on Linux.

libacl1-dev

ACL support lets Emacs understand and preserve POSIX Access Control Lists when manipulating files. This matters in some multi-user, enterprise, or carefully permissioned environments. In 2025, it’s still optional: valuable if you need it, but many personal setups won’t notice if it’s missing.

libgmp-dev

GMP is a high-performance big-integer library. Emacs has bignum support, and GMP can improve performance or provide an implementation path depending on how Emacs is configured and what the distro provides. In 2025 it’s still optional, but most students can treat it as “nice to have”.

GUI / rendering stack (for --with-pgtk, --with-x, --with-cairo, --with-xft builds)

This group determines whether you get a graphical Emacs, and which windowing system it targets. On Linux today you typically choose either:

  • Wayland-first PGTK build (--with-pgtk), which uses GTK directly, no X11 required, or a classic X11 build (--with-x), which uses X11 libraries and may use GTK, Lucid, etc. depending on options.

Required for a Wayland-first PGTK build (--with-pgtk)

libgtk-3-dev

GTK is the GUI toolkit Emacs uses when you build the GTK/PGTK variants. If you configure with --with-pgtk, GTK 3 development headers are what make that possible. So yes: for a GUI Emacs in this style, you need it. For a pure terminal build, you don’t.

libcairo2-dev

Cairo is a 2D graphics library used for drawing text and shapes smoothly. In Emacs builds that use it (--with-cairo), it improves rendering and is part of the modern graphics stack. In 2025, it’s recommended for GUI builds, and many people consider it the default choice.

libfreetype-dev

FreeType rasterizes fonts (turning font outlines into pixels). It’s fundamental for good font rendering in GUI Emacs. In 2025, if you build a GUI Emacs, you almost certainly want this.

libfontconfig1-dev

Fontconfig discovers fonts installed on the system and applies user/system font configuration. Without it, selecting and managing fonts is more limited. Today, for GUI Emacs, this is recommended.

libharfbuzz-dev

HarfBuzz handles text shaping: ligatures, complex scripts, correct positioning for many writing systems, and generally “modern typographies.” In 2025, it’s strongly recommended if you want the best text rendering experience, especially for non-Latin scripts or typographic features, as found often in non-English languages.

Required for a classic X11 build (--with-x)

libx11-dev (and related X11 libraries)

These provide the X11 client headers and related interfaces. They are required if you build the classic X11 Emacs, or if you enable features that still rely on X11 even on mixed systems. For a pure PGTK/Wayland-first setup in 2025, you can often skip them. For an X11 build, they’re required. Some builds need extra X11-related -dev packages (XInput, X extensions, XCB helpers), depending on distro and enabled features.

libxft-dev

Xft is an X11 font rendering interface. If you are building an X11 GUI Emacs and explicitly configure with --with-xft, this is part of that path. In 2025, it depends on what you’re building: for a Wayland-first PGTK build it may be unnecessary, but for classic X11 builds it can still matter.

libcairo2-dev

Cairo is a 2D graphics library used for drawing text and shapes smoothly. In Emacs builds that use it (--with-cairo), it improves rendering and is part of the modern graphics stack. In 2025 it’s recommended for GUI builds, and many people consider it the default choice.

libgtk-3-dev

GTK is the GUI toolkit Emacs uses when you build the GTK/PGTK variants. If you configure with an with an X11 toolkit (without --with-pgtk), using only GTK development headers, you may also need libgtk-3-dev. If you use the Lucid/Motif toolkit instead, libgtk-3-dev is not required.

Not needed for either GUI path

  • For a pure terminal build (no GUI), you can generally skip all of the above GUI/X11/GTK packages.

Image format support (optional but common for a “full” GUI Emacs)

Emacs can display images inline (in buffers, help pages, customize UI, icons, etc.), but each image format is enabled by the corresponding system library. A minimal Emacs works without these, but a “desktop Emacs” usually includes several.

libpng-dev

Enables PNG image support, which is widely used for icons and screenshots. In 2025, this is optional, but it’s one of the most commonly installed image libs because PNG is everywhere.

libjpeg-dev

Enables JPEG image display. Optional in 2025, but useful if you view photos or web-derived content inside Emacs.

libgif-dev

Enables GIF support (including simple animations in some cases). Optional, and mostly a convenience feature, but what kind of software doesn’t handle GIFs?

libtiff-dev

Enables TIFF support, mainly relevant for publishing/scanning workflows. Optional in 2025; many students won’t need it.

libwebp-dev

Enables WebP images, which are common on modern websites. Optional, but increasingly useful in 2025 if you interact with web content.

libavif-dev

Enables AVIF image support if Emacs detects it. AVIF adoption has grown, so this can be handy. Optional in 2025.

libopenjp2-7-dev

Enables JPEG 2000 support. This is a niche format, seen more in some academic/archival contexts. Optional in 2025.

librsvg2-dev

Enables SVG rendering via librsvg. This is especially useful because modern icon themes and some documentation assets are SVG-based. Optional, but very nice to have for a polished GUI Emacs in 2025.

liblcms2-dev

Provides color management support (ICC profiles). This matters if you care about accurate color handling in images. Optional for most users in 2025.

libxpm-dev

Enables XPM support, an older X11-era icon format. Some legacy assets still use it. Optional in 2025, and mostly relevant for compatibility.

libmagickwand-dev

Enables ImageMagick integration, which can add support for many additional image formats through a single dependency. The tradeoff is that it’s a large dependency and expands the “attack surface” of your build. In 2025, it remains optional; many people either love it for broad format support or avoid it deliberately for simplicity and security.

Native compilation (--with-native-compilation) (optional)

Native compilation (often called “native-comp”) lets Emacs compile Lisp to native code via GCC’s JIT infrastructure, which improves performance for most workloads.

libgccjit-dev

This provides the headers and development files needed to build Emacs with native compilation support.
Optional in 2025, but widely used. The important practical note is that the JIT library version generally needs to match your GCC version on some distros.

libgccjit0

This is the runtime library Emacs needs in order to use native compilation after it’s built. Installing libgccjit-dev usually pulls it in automatically, but conceptually it’s the “runtime half” of the feature. If you build with native-comp in 2025, you need this available at runtime.

Tree-sitter (--with-tree-sitter) (optional)

Tree-sitter provides fast incremental parsing, which modern programming modes can use for better syntax highlighting and structural editing. Emacs integrates with it when built with tree-sitter support.

libtree-sitter-dev

This is the development library that enables tree-sitter integration during the build. In 2025, it’s optional, but increasingly common because many users want tree-sitter-based modes.

XWidgets (--with-xwidgets) (optional; heavy)

Xwidgets let Emacs embed certain GUI widgets in buffers, like, for example, buttons, a scrollable area, or an embedded web view (xwidget-webkit), which renders web pages using WebKitGTK. This is powerful, as it can bring in interactive web content and richer UI elements, but it pulls in a large dependency chain. Despite the name, by the way, XWidgets are not X11-specific.

libwebkitgtk-6.0-dev

This is the development package for WebKitGTK, used to render web content inside Emacs when xwidgets are enabled. In 2025, it’s still optional and only worth installing if you explicitly want --with-xwidgets, because it adds weight and complexity to the build.

Mailutils integration (--with-mailutils) (optional)

Emacs can integrate with external mail handling tools for moving mail from spool files and related workflows.

mailutils

GNU Mailutils provides tools like movemail integration when you configure Emacs to use it. In 2025, this is optional and only relevant if you use those specific mail workflows; many users rely on IMAP/SMTP (gnus, mu4e, notmuch, etc.) and/or Maildir, and therefore do not usually need Mailutils.

Obsolete / no longer typically needed

These items show up in older guides, but they are usually not required for a current Emacs build in 2025. You may still see them mentioned because documentation on the internet lags behind current Emacs releases.

libjansson-dev / libjansson4

Jansson was historically used for JSON parsing. However, on a typical 2025 Linux build, there is a new native JSON parser that does not rely on Jansson (introduced in Emacs 30.1+). It’s built in and up to 8x faster, rendering the jansson library obsolete.

liblockfile-bin / liblockfile1

These were used for certain file-locking mechanisms. Current Emacs on Linux typically relies on internal or OS-standard approaches instead. In 2025, it’s obsolete for mainstream builds.

emacs-snapshot-common

This is a packaging artifact from some distro workflows around snapshot builds, not a normal “build Emacs from source” dependency. In 2025, it’s obsolete when compiling Emacs yourself from upstream source.

emacsen-common

Historically part of Debian/Ubuntu Emacs policy integration (e.g., coordinating site-wide lisp and add-on packages). Most modern setups don’t need it, as Emacs packaging and configuration no longer rely on -el helper packages in the same way. In 2025, it’s obsolete, unless you’re dealing with legacy Debian packaging workflows.

dictionaries-common

Previously used to provide system dictionary integration (often pulled in via emacsen-common). Current Emacs spell-checking is typically handled through Hunspell or Enchant-based tooling instead. In 2025, it’s more or less obsolete in mainstream builds.

aspell / aspell-en

Aspell was a common spell-check backend for Emacs, but most current configurations use Hunspell or Enchant, and many distros default to those programs. In 2025, not exactly obsolete, but not needed unless you specifically prefer Aspell.

gettext-el

An Emacs support add-on for GNU gettext that used to be packaged separately in some distros. It’s generally no longer required as a standalone dependency for typical Emacs installs or builds. In 2025, it can be consider obsolete.

Installing build dependencies (Linux, Emacs 30.2)

Most Linux distributions ship with many of the libraries or “parts” ./configure probes your system for when you build Emacs 30.2 from source. But, the default package set (and even the default enabled repositories) may not include the development packages – typically the -dev / -devel variants that contain headers and .pc metadata used by pkg-config.

In other words: you may already have, say, PNG or TLS support at runtime on your machine, but still be missing libpng-dev or libgnutls-dev, and then Emacs will quietly build without those capabilities.

When distro sources aren’t enough (and when they usually are)

On mainstream distributions (Ubuntu/Debian, Fedora, Arch, openSUSE), most Emacs build dependencies are available directly from the official repositories – especially in 2025. However, if you’re on an older release, a minimal install, or you want newer variants (e.g., a newer tree-sitter, libgccjit, or image codecs), you might discover the packages aren’t available from your enabled sources. At that point, you may need to:

  • Enable additional official repository components (common on Ubuntu: universe, multiverse)
  • Add a third-party repository or PPA (Ubuntu) that provides the missing -dev packages
  • Or build/install a dependency from source (less common, but sometimes necessary)

Keep in mind: dependency lists also differ on other platforms – an MSYS2 build on Windows or a macOS build, for example, will use different package managers and library names, even though the roles of the libraries are similar.

Example: installing dependencies on Ubuntu/Debian (bash/zsh)

Below is a typical “kitchen sink” set of packages that enables most modern Emacs features (TLS, native-comp, images, tree-sitter, SQLite, etc.). You can paste this into bash or zsh and execute it to install the packages; backslashes are just line continuations.

Use sudo apt install -y to install. The -y argument means ’do not ask for confirmation’.

sudo apt install -y \
  build-essential pkg-config libncurses-dev texinfo \
  autoconf automake autopoint libtool \
  libgnutls-dev zlib1g-dev libxml2-dev libsqlite3-dev libacl1-dev libgmp-dev \
  libgtk-3-dev libcairo2-dev libfreetype-dev libfontconfig1-dev libharfbuzz-dev libxft-dev \
  libpng-dev libjpeg-dev libgif-dev libtiff-dev libwebp-dev libavif-dev libopenjp2-7-dev librsvg2-dev liblcms2-dev libxpm-dev \
  libgccjit-dev libtree-sitter-dev

If apt reports that some packages “cannot be located,” that’s the signal to check whether your enabled repository sources include them (or whether you need an additional repo/PPA for your distro release).
